# Architecture — key patterns in full

> Part of the codebase guide — start at [`CLAUDE.md`](../CLAUDE.md).

### 1. `appContext` — Central Dependency Injection
Shared runtime state lives in **`src/core/appContext.js`** in typed buckets:
```js
appContext.entities   // otherPlayers, weapons
appContext.systems    // playerControls, rapierWorld, rbToMesh
appContext.uiState    // appState
appContext.settings   // user preferences, startupPhases
appContext.debugFlags // PERF, DEBUG_CONSOLE
```
`exposeDebugGlobals.js` mirrors these onto `window.*` (compat shims + dev console). New code should go through `appContext` rather than adding raw globals.

### 2. Feature Facade Pattern (`src/features/`)
Files in `features/` are **thin re-export + lazy-load wrappers** to enable Vite code splitting. `combatFeature.js` re-exports `projectiles.js` and lazy-loads the weapon modules (shield, pistol, foam sword); `uiPanelsFeature.js` lazy-loads the shop. When adding new heavy features, add a facade here.

**Modes loaded on first use:** Town (+ townNet, diving, the sea start and Story — `src/town/townModules.js`), Multiplayer (`duelMode.js` + `matchMode.js`) and the tutorial (`showdownTutorial.js`) are separate chunks, not in the startup bundle. `MODE_MODULES` / `_modeGroup` / `_loadModeModules` (before `_startMode` in `bootstrapGameApp.js`): the mode handler loads a mode's group alongside its map, then calls that group's `_make*` (the old `x = createX(ctx)` lines, now `const _makeX = ({ createX }) => { … }` where they were), then `_startMode`; a failed load → `_modeLoadFailed` (back to the start screen). `_prefetchModeModules` fetches the chunks at idle a few seconds after boot. Until made, `town` / `story` / `seaStart` / `townNet` / `_townDive` / `duelMode` / `matchMode` / `showdownTutorial` are `null` — **guard every use with `?.`**, and don't import those modules statically from the main chunk (put shared constants in a small module, like `matchConfig.js`).

### 3. Multiplayer: lobby + duel rooms (Multiplayer mode only)
- Peer multiplayer only exists in Multiplayer mode and a shared Town: `startMultiplayer(roomId)` / `stopMultiplayer` in `bootstrapGameApp.js` create/destroy the `Multiplayer` instance (Showdown and the tutorial are single player; `multiplayer` is `null` there — guard every use). Town: `townNet` (`src/town/townNet.js`) starts it in room `town-<roomId>` and stops it on leaving Town (duelMode's delayed stop skips while `townNet.isOn()`); `_netRecipients` / presence / `_getPvpTargets` include the town's players; message type `town`
- Firebase Realtime Database = `peers/<id>` ({name, roomId}) lists everyone online (the lobby list), `rooms/<roomId>/<id>` drives who connects to whom; the shop stock is global (`merchantInventory`)
- Rooms: everyone starts in `lobby`; a duel moves both players to `duel-<challengeId>` (`joinRoom`) and back afterwards. Battles: a solo party host waits in `mm-<mode>-<rule>` (the matchmaking queue), a party with guests in `party-<hostId>`, the battle itself in `match-<matchId>`
- PeerJS WebRTC message types: `presence` (position/animation/equipment), `projectile`, `duel` (`op`: challenge/accept/decline/cancel/state/hit/blocked/dead/leave — see `duelMode.js`), `match` (party/queue/battle ops — see the header of `matchMode.js`). Game traffic is sent only to the duel opponent / the other battle players (`sendTo`, `_netRecipients`); presence from anyone else is ignored
- Battles: the host (whoever pressed Start) simulates the bots, owns the pickups (`take` → `taken`) and the score (`dead {by}` → `kill {v, by, sc}`), and decides the winner; bot state is broadcast (`bots`), humans hit bots via `botHit` to the host. The host leaving ends the battle
- Duel hits: the attacker's sword check detects the hit and sends `hit`; the victim applies the damage and sends `dead` when it dies
- One peer per room elected "host"; others connect to it (star)
- Topology mode configurable via `VITE_NETWORK_TOPOLOGY_MODE` env var
- The phone controller has its own PeerJS connection to the game (`_attachPhoneSwordConn` in `bootstrapGameApp.js`; the newest phone connection replaces an older one — `_phoneSwordConn`); TURN servers come from `/api/turn-credentials`. The game's gyro peer (`_createGyroPeer`) stays registered on the signalling server so a phone can reconnect mid-game: it reconnects on `disconnected` (backoff, and at once on `visibilitychange` / `online` / `focus`), is recreated when destroyed, and retries its fixed ID while a stale registration holds it (`_fixedPeerId` = a hash of `profileNameKey` — one phone URL per profile — or, for guests, of a per-browser device ID kept in localStorage + cookie `sq:guestDeviceId`, so the URL survives refreshes); the phone page retries `peer-unavailable` / times out a connection that never opens (`connectToGame` in `public/phone-sword.html`)

### 4. World: maps per mode
`MAPS` in `bootstrapGameApp.js` lists the maps: `islandTown` (`public/mappacks/island_town.mappack`, loaded with `MapLoader` from `src/map/MapLoader.ts` — the map editor's runtime, edited for the game: `userData.mapObject` on placed objects, each placed object wrapped in a group so the `normalisePivot` offset survives (the editor's copy overwrites it, misplacing GLBs whose origin isn't at their bottom-centre), KTX2 loader disposed, fetch errors thrown, model files loaded in parallel, the meshopt decoder set on its GLTFLoader (packs run through `scripts/optimize-mappack.mjs`), the `sea: false` load option (no ocean plane, a small seabed apron — `SEA_APRON_EXTENT`); replace it with a new editor copy and re-apply those; run every exported pack through `npm run optimize:mappack -- <pack>` — WebP model textures + meshopt, ~2.5× smaller) (scaled ×1.4 by its `scale` — spawn, `DUEL_LOCATION` / `ARENA_LOCATION` and `STAGE_ROUTES` are in scaled world units; the water sampler un-scales its queries) for Showdown, the tutorial, Town and Multiplayer, and `classic` (`public/glb_map/map.glb`, ×5) for Classic (`mapForMode`). The default map loads at boot; the mode handler (`setModeHandler`) awaits `_setActiveMap(mapForMode(mode))` before starting a mode — it loads a map the first time (cached after), swaps it into the scene, clears the height cache, re-registers the bullet meshes (`registerMapMeshes`) and the spawn centre (`setSpawnCenter`), and a changed map teleports the player to its spawn. Each map's meshes get a `three-mesh-bvh` BVH and one downward-raycast height resolver (`registerTerrainHeightResolver`, `src/environment/terrainHeight.js`) casts against the active map's ground meshes (cached on a 0.5 m grid — `_glbCellLayers` — and blended bilinearly between the 4 grid points round x, z — `_glbLayers`, edges over `_GLB_BLEND_MAX_STEP` kept sharp — so slopes have no stair-steps; the player's small step ups / downs are eased too — `GROUND_EASE_*` in `controls.js`). Everything that needs ground height (`getTerrainHeight`, `getSpawnY`) goes through that resolver. Mappack grass / scatter (instanced) is neither ground nor solid; objects matching a map's `noGround` (trees) and the water meshes (`MAP_NOT_GROUND`: `sea` / `seabed` / `water`) stop bullets but aren't stood on. Trees' trunks are solid instead: `_measureMapTrunks` (in `_setActiveMap`, one `measureTrunk` per tree model, carried over to its copies) → `setMapObstacles` (`src/environment/obstacles.js` — the player slides round them in `PlayerControls._walkStep` / is pushed out in `processMovement`) + a Rapier cylinder per trunk for enemies' bodies (`_syncTrunkColliders`); the leaves stay walk-through. The map editor's per-model collider setting isn't exported to the `.mappack` and isn't read. A pack with a sea level (the island) sets the ground floor `SEA_WADE_DEPTH` under it (`setTerrainFloor`; the flat Rapier ground collider's top follows it too — `_syncPhysicsGround` — so enemies' dynamic bodies can go below y = 0), so characters wade in the sea instead of sinking; `_isOverWater(x, z)` (MapLoader's `sampleMapWaterLevel`, bridges count as dry) makes `_psPathSteepness` steer stage paths away from water (`PS_PATH_WATER_PENALTY`). The first map loaded is the art-style reference (its objects' textures; KTX2 textures are skipped by `artStyle.js`). Multiplayer spots (`DUEL_LOCATION`, `ARENA_LOCATION`) are island town coordinates. A mappack with a sea can carry `floating` GLB props (the island's pirate ship): loaded in `_loadMap` (`_loadFloatingProp`, pack units, origin on the sea surface), stylized, bobbing on the swell (the map's `animate(t)`, called each frame — `FLOAT_*`); they stop bullets and are kept out of the map's height raycast (`noGround` — their masts would be the ground), but one with `deckMaxY` (the ship: 1.5 model units) is ground of its own: `_floatingGroundHeight` (a second, uncached height resolver — it bobs) casts down onto its highest upward-facing surface no higher than `deckMaxY` (the deck — masts / yards / sails ignored), so it is climbed from the water like any wall and stood on. One with a `deck` rect (the ship) can sail: open roam's voyage moves its `holder` (`_voyageUpdate`, see the area docs (`docs/areas/`)) and moves it back to its `anchor` afterwards. A map's `islands` (Tree Island) are other mappacks in the same world, out on its sea — streamed in from Town's canoe, no map switch (see the Islands row in the area docs (`docs/areas/`)).

### 5. Stages (`_ps*` in `bootstrapGameApp.js`)
Between stages the player is in the **village** (`src/village/villageMode.js`, see the area docs (`docs/areas/`)), built around wherever they stand (or at the stage route's first point); the villager stands on the next stage's path and gives a quest for it (accepting starts the stage). A stage with a hand-authored route (`STAGE_ROUTES` in `src/map/stageRoutes.js`, recorded with Settings → Dev → Free Roam) auto-walks along its waypoints (following the line, not touching each point — see the area docs (`docs/areas/`)); otherwise it picks the flattest direction from the start (`_psPickPathAngle` — picked when the village opens and passed to `_psStartStage` / `_psBuildStage`). `_psBuildStage` places swordsmen, bombers and coins along it (`_psBuildStage`; from the village they start `PS_VILLAGE_EXIT_DIST` m out so the player walks out first), then auto-walks the player between fights. Enemies (`EnemyPlayer`, `BombThrowerEnemy`) live in the `hordeEnemies` array (historical name).

### 6. GLB Character + IK Arms
Players render `public/models/glb_characters/village_boy.glb` (`glbCharacterConfig.villageBoyUrl`) by default (Showdown lets them pick an unlocked character, Multiplayer battles a roster character); Stage enemies' characters are preloaded in the village (`preloadCharacterModel`) and a queued enemy only spawns once its model is in (`isCharacterModelSettled`), so none fights invisible. EnemyPlayers without a `characterUrl` cycle through `pumpkin.glb`, `antler_guy.glb` (`glbCharacterConfig.antlerGuyUrl`), `frog_man.glb` (`glbCharacterConfig.frogManUrl`), `gemhorn_rigged.glb` (`glbCharacterConfig.url`, the default) `wizard.glb` (`glbCharacterConfig.wizardUrl`) and `tree_creature.glb` (`glbCharacterConfig.treeCreatureUrl`) per spawn (Showdown stages pass one) — all share the Mixamo skeleton, picked with the `url` option of `createGLBCharacterInstance`. No character has shell fur any more (`glbCharacterConfig.fluffy.shells` = 0 — bouncy secondary motion only); per-model fluffy overrides go in `glbCharacterConfig.fluffyByUrl`. Every model is scaled to the same `targetHeight` from its bind-pose bounds; per-model size multipliers go in `glbCharacterConfig.heightScaleByUrl` (tree creature and gemhorn 1.4×, villager (Pemberton) 1.1×, village boy / girl 0.8×; a smaller character also gets a lower player camera — `cameraHeightByUrl` → `characterCameraHeight`, used by `PlayerControls`: village boy 0.9×). `fluffyCharacter.ts` retargets the Mixamo clips (walk/run/idle — all in `public/models/animations/animations.glb`, one action per clip, addressed `animations.glb#<name>`) onto it and adds fur; a moving character plays the `Slow Run` clip (`runClip`) instead of the walk once its ground speed — measured from its world position in `GLBCharacter.animate` (`_updateSpeed`), so the same for the player, remote players and enemies — passes `glbCharacterConfig.runSpeed` (3 m/s; back to the walk below `runSpeed × runStopRatio`); the clip drives everything **except** the arm chains. Arms are posed each frame by a stretchy two-bone IK (`GLBCharacter.solveArm`) toward invisible floating-hand groups, which are also the weapon attach points (`userData.proceduralHand` markers, preferred by `Weapon._getHandBone`). The GLB and clips face +Z (game forward) — no Y180 needed. Hand labels are mirrored: the `'right'` floating hand is at local +X, i.e. the anatomical left arm. Per-character weapon hold: `glbCharacterConfig.holdByUrl` (`characterHold(url)` → `{ grip, sword }`) scales the floating-hand grip targets in `updateProceduralPlayerRig` / `updateRemotePlayerRig` and the held sword (`FoamSword.update`, `createSwordMesh`) — village boy grips at 0.76 with a 0.8 sword. Which arms the IK drives is per hand (`GLBCharacter.setArmIKHands({ left, right })`, the clip animates the others and restarts to pick them up): the local player with nothing equipped (✋ Hands, the village…) has both arms on the clip — the gyro doesn't move an empty hand; only while something held asks for it (Town's hose — `userData.gyroHandAt`, refreshed each frame) the anatomical right arm (`'left'` hand) goes on the IK, following the phone gyro (`userData.gyroArmQuat` / `gyroArmTime`, set in the phone-sword gyro loop of `bootstrapGameApp.js`, `GYRO_ARM_*` in `playerModel.js`). A held pose: `GLBCharacter.playPose(url)` loops a clip over the whole body (IK suspended) until `endPose()` — Town's broom sits the player down with `sitClip` (the `Sitting` clip), Town's cart crouches them with `crouchClip` (the `Crouch` clip), wall climbing loops `climbClip` (the `Climb` clip); `playPose(url, { armIK: true })` keeps the IK arms on the IK (Story: sitting on the stone holding the flute; the broom: whatever is in hand). On death, `GLBCharacter.playDeath()` plays the `Flying Back Death` clip once over the whole body (IK suspended, hands follow the palms) until `revive()`; EnemyPlayer keeps its ragdoll during it, with knockback capped by `DEATH_KNOCKBACK_CAP`. Bomb blasts reuse the clip without dying: `EnemyPlayer.applyBlastKnockback()` (ragdoll + `playDeath()`, `revive()` in `_endRagdoll`, force/cap `BLAST_KNOCKBACK`) and `_blastPlayer()` in `bootstrapGameApp.js` for the local player. `BombThrowerEnemy` uses the same GLB with `armIK: false` (clips drive the arms, no floating hands): `playAction(glbCharacterConfig.throwClip)` plays the `Throw` clip once and releases the bomb at `THROW_RELEASE_AT` of the clip; between throws a bomb mesh is snapped to the anatomical right palm (`getPalmWorldPosition('left')` — labels are mirrored). Blasts from other throwers play the death clip for `BLAST_STUN_MS`, then `revive()`.

**Mii characters** (`mii1.glb`, later `mii2.glb`… — `isMiiCharacterUrl` matches `/miiN.glb`) have no shoulders, arms or hands. `_buildArm` finds no chains, so `solveArm` leaves the floating hands where the game put them and `getPalmWorldPosition` returns a point beside the body (`palmFallback`, bomber / player bomb). Their hands are drawn by the sword: a Mii holds the Wii sword (`wii_sword.glb`, `SWORD_VARIANTS.wii` in `swordModel.js`) whose instances carry two brown ball hands on the handle. `createSwordModelInstance({ characterUrl })` picks the variant (`swordVariantForCharacter`); `FoamSword` swaps its model when the player's character changes, `EnemyPlayer._buildSword` uses the enemy's character, and `createSwordMesh(characterUrl)` (duel / battle opponents) the opponent's. Miis are Classic only. New Mii: add the GLB, a `glbCharacterConfig` url and add it to `CLASSIC_MII_URLS` (not `MATCH_CHARACTERS`).

**Unrigged characters** (no skeleton — `villager.glb` for now) load through the same `createGLBCharacterInstance`, but `GLBCharacter` gets a `StaticRig` instead of the `FluffyCharacter`: no clips or arm IK, just procedural motion (breathing idle, a walking bob, tipping over on death) and `palmFallback` hands. Rig the GLB (Mixamo skeleton) and it uses the normal path automatically.

### 7. Start screen + tutorial
After login the start screen shows only **Start Game** (runs the tutorial) until the profile has `tutorialCompleted: true`; after that it shows **Tutorial**, **Story**, **Showdown**, **Classic**, **Town** and **Multiplayer**. Auth resolves as soon as the player is logged in, so the game (and the settings panel) loads behind the start screen; a mode picked before it's ready is queued and started when `setModeHandler` is set (the auto phone-QR popup is deferred until a mode is picked, `autoShowPhoneSwordQr`). When the tutorial finishes, `arcadeOverlay.showStartScreen()` brings the start screen back and the mode handler starts the next mode in the running game. The ⚙️ settings button (`#settings-button`) sits above the start screen, the stage overlay and the Multiplayer lobby (z-index in `styles.css`) and stays visible in every mode (Classic included), hidden until `body.settings-ready` (set once `initSettingsPanel` has run — the default map loads in parallel, `_defaultMapReady`, and the boot never waits on it: the game loop starts without it (the guest's sea start plays meanwhile), a picked mode waits on it in the mode handler, and the player is put on the map's ground at the spawn once it's in unless out on the sea). While a mode is running the settings panel shows a **⬅ Back to Lobby** footer button (`buildFooter` in `settingsPanel.js`) → `appState.returnToLobby` (stops the tutorial via `showdownTutorial.stop()`, exits Multiplayer / Classic, `_resetForMenu`, `showStartScreen`). The tutorial script (`src/tutorial/showdownTutorial.js`) drives enemies through `EnemyPlayer.script` (`passive` / `block` / `windup`) and the bomber's `throwsHeld` / `aimAt`, and touches the game only through `tutorialCtx` in `bootstrapGameApp.js`. While it runs, health never drops (`localHealth` setter), auto-buy is paused (it buys scripted), and tutorial enemies drop no coins and don't count as kills (`_tutorial`).

### 8. UI design system (`styles.css`)
Every screen — start screen, settings / shop / leaderboard (`.settings-shell`), village panels / buy card, phone QR / calibration popups, Multiplayer lobby / battles, tutorial, game over, HUD — shares one dark glass look. The top of `styles.css` holds the **tokens** on `:root` (`--font-ui` Inter / `--font-display` Outfit, loaded from Google Fonts in `index.html`; `--surface*`, `--border*`, `--text*`, gold `--accent*`, status colours, `--radius-*`, `--shadow-*`, `--menu-bg` for full-screen menus, `--scrim` for modal backdrops) and three **shared components** applied by grouped selectors: **panel** (`.ui-panel`, `.arcade-shell`, `.settings-shell`, `.duel-lobby-panel`, phone popups…), **button** — gold primary (`.ui-btn`, `.arcade-button`, `.settings-button`…), glass secondary (`.ui-btn-secondary`, `.arcade-secondary`, …) and ghost (`.ui-btn-ghost`, `.arcade-guest`, back buttons) — and **chip** (`.ui-chip`, settings / leaderboard tabs; selected = `.is-active` / `.active`). New UI: use the `ui-*` classes (or add the new class to the matching group) and the tokens, not new colours / fonts. HUD elements are `--surface-hud` pills without `backdrop-filter` (it would re-blur the 3D view every frame). Classic keeps its Wii-style lettering (stage banner, Ready/Go!, combo) but uses the shared panel/buttons. `public/phone-sword.html` repeats the tokens it needs in its own `:root`.

**Icons in place of emoji:** `public/assets/ui/icons/pixelIcons.js` (a plain script in `index.html` and `public/phone-sword.html`, before the app) maps emoji → a cell of one of two sheets (`SHEETS`): `pixel-icons.webp` (pixel art, lossless — `PIXEL`, [row, column], drawn pixelated) and `painted-icons.webp` (painted, one atlas of the two painted packs — `PAINTED`, wins where both have one: ❗ ❓ 📍, coin, heart, sword, shield, chest, backpack, fire, canoe, gun, house, lock, bullets, the characters' portraits, mood faces, ★ / ☆, the bell…; each pack cut from its dark background — blobs by distance from the background colour, flood-filled from the edges + enclosed holes, edges feathered, packed at 64 px, WebP q80). A MutationObserver wraps every mapped emoji in the DOM in a `<px-icon>` (the emoji stays as its transparent text, so `textContent` is unchanged), so UI code keeps writing plain emoji; canvas text goes through `window.pixelIcons.drawText` / `measureText` (`makeTextSprite` in `villageMode.js` — 3D signs / markers). An emoji with no icon in `ICONS` stays an emoji; to add one, add its cell. Direction: minimal on-screen UI and messages (Town talk = subtitles, no name tags over townsfolk). **Emoji only where it is the content**: item / goods / character icon fields (`emoji:`), counters (coins, bag, bombs, bubbles, kills, mana), prices next to a number, ❗ / ❓ / 📍 markers, ★ stars and icon-only buttons; button labels, feed lines, toasts, banners, speech and tutorial text are plain words ("+3 coins", "Shop", "Get out"). Button labels quoted elsewhere in this guide may still show the emoji they used to carry.

### 9. PIN Auth
No OAuth. Player registers with name + numeric PIN. PIN is `SALT + SHA-256` hashed client-side via Web Crypto, stored in Firebase. Hash cached in cookie for auto-login.

**Guest play:** the app opens as a guest on the start screen (`startAsGuest` in `createArcadeOverlay`; the sea start — `startAsGuest({ seaStart: true })` — is off) unless a signed-in player is remembered (stored PIN → auto-login). The start screen's "Sign In" / "Switch user" button (`data-arcade-switch`, kept visible when returning from any mode via `showStartScreen`) reloads the page with the `sq:showLogin` sessionStorage flag, which opens the login form instead; "Play Without Signing In" there (`data-arcade-guest`) goes back to guest. Guest play skips auth with a random name (`randomGuestName`) and an in-memory profile (`buildGuestProfile`, all modes offered). `initCore` then has `isGuest` true and `profileNameKey` null — every profile save (`saveStats*` wrappers, stage/characters/tutorial/phoneSwordStats, localStorage `ps_*` keys) is skipped when the key is null, `playerName` isn't stored, and renaming only changes the session name. Guard new profile writes on `profileNameKey`.
